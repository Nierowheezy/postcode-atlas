# Postcode Atlas — Codebase & End-to-End Architecture

Generated from a full read of the repository at HEAD (`fcc927b feat: conversation context (10)`). This is a read-only descriptive report of how the codebase is put together today, organized bottom-up through the layers, then top-down through a request. It is intended as durable orientation for new agents and reviewers.

> Scope: covers the shipped NDAPS (Nigerian Digital Alphanumeric Postcode System) cartographic explorer and the Ask Atlas conversational layer on top of it. Covers the local dataset cache, the NIPOST gateway client, the Ask Atlas tool layer, the provider failover chain, the UI shell, and the build/deploy shape. Does not reproduce the BuildFlow planning docs.

---

## 1. High-level shape

The project is a **static React 19 + Vite 8 single-page application** with a single server-side entry point.

```
Browser (Vite dev) or Vercel Edge/Function (production)
  │
  │  POST /api/ask   ←→  src/server/ask/handler.ts  (validation + cache + chain)
  │                                           ├─ src/server/ask/providers.ts   (LLM fan-out)
  │                                           ├─ src/server/ask/chain.ts        (failover order)
  │                                           └─ src/server/ask/prompt.ts       (system prompt)
  │
  │  GET atlas-data.json        ←→  public/atlas-data.json (committed NDAPS hierarchy snapshot)
  │  GET version.json           ←→  dist/version.json (build-time version manifest)
  │  GET/POST NIPOST gateway    ←→  api.postcode.gov.ng  (via src/lib/api/postcodeClient.ts)
  │
Client app  ──►  src/main.tsx
                src/App.tsx          (single state owner, the shell)
                src/components/**    (map, search, inspector, drawers, modals, ask sub-panels)
                src/lib/**           (ask: types/api-types/useAskAtlas/responder/errors/queryClient)
                                     (tools: types/schemas/registry/provider/executors)
                                     (atlas: dataset/store/storage)
                                     (api/postcodeClient, geo/*, version)
```

**Line count:** ~9,800 lines across 60 source files (`src/`, `api/`, `scripts/`). `src/App.tsx` is the heaviest at 618 lines; `src/lib/ask/responder.ts` at 830 lines is the second.

**Key architectural decisions, stated up front:**

1. **No backend by design.** The app is a static bundle. The NIPOST gateway is called directly from the browser using a publishable key (`nipost_pk_…`). The only deployed server logic is the Ask Atlas `/api/ask` function, which exists purely so LLM provider keys never reach the browser.
2. **One state owner.** All UI state — selected location, breadcrumbs, mode, modal open flags, hunt state, map viewport, version/availableVersion — lives in `App.tsx` (`PostcodeAtlasContent`, lines 43–608). Components are presentational and receive props + handlers.
3. **Ask Atlas is a tool-calling overlay.** It does not replace the map UI; it drives it. The model emits `navigateMap`/`getNearby`/`getPostcode` tool calls, the client executes them locally against the dataset cache, and the results are fed back. The derived answer (lookup, result list, decoded postcode, nearby list, map action, referent) is computed on the client from the executed tool turns — never from reply prose.
4. **Local-first data, read-through fallback.** States and LGAs ship in `public/atlas-data.json` (~35 KB, 37 states / 774 LGAs) and hydrate into IndexedDB on load. Districts and areas are intentionally omitted from the snapshot (NDAPS exposes ~222k districts / ~5M areas, code-only, ~290 MB uncompressed), so those hierarchy levels fall through to the gateway at query time.

## 2. The data layer (bottom)

### 2.1 Static hierarchy snapshot — `public/atlas-data.json`

- Generated by `scripts/build-atlas-dataset.mjs` (`npm run dataset`), committed to the repo, ~35 KB.
- Payload shape:
  ```json
  { "version": "1.1.0", "generatedAt": "<ISO>", "counts": {"states":37,"lgas":774,"districts":0,"areas":0},
    "states": [{code, name}], "lgas": [{state, code, name}],
    "districts": [], "areas": [] }
  ```
- Districts and areas are `[]` on purpose (see script header and `store.ts` fallback logic). Only states and LGAs are bundled.
- Served directly by the static host and by `vercel.json`'s explicit `/atlas-data.json` rewrite (so the SPA fallback doesn't swallow it).

### 2.2 Local dataset cache — `src/lib/atlas/store.ts` + `storage.ts` + `dataset.ts`

- **Store (`store.ts`):** the public read API and the hydration controller. Exposes `atlasStore = { ensureHydrated, getStatus, getStates, getLgas, getDistricts, getAreas, searchLocations, getPostcode, getDiscoveryPoints }`.
  - `ensureHydrated()` is non-blocking, idempotent, single-flight (module-level `hydration` promise reset in `.finally`). Reads the `meta` record; if `meta.version === APP_VERSION` (`1.1.0`), no-op; otherwise fetches + writes the snapshot. A failed write keeps the stale dataset and retries on next load. Fired once from `App.tsx:100` via `void atlasStore.ensureHydrated()`.
  - `getStates` / `getLgas` / `getDistricts` / `getAreas` all read IndexedDB first; on an empty result they fall back to `postcodeApi.fetch*` gateway calls and normalize the shape to the local type.
  - `getPostcode(code)` checks bundled landmarks first, then the gateway.
  - `searchLocations(q)` does prefix + contains matching over the four local stores + discovery points, capped at 12 results; if still empty and hydrated data exists it retries contains; if still empty it falls back to `postcodeApi.autocomplete` (segment-aware). Returns `LocationCandidate[]` (types defined in `dataset.ts:60-67`): `{type:'state'|'lga'|'district'|'area'|'landmark', code, name?, state?, lga?, coordinates?}`.
- **Storage (`storage.ts`):** raw IndexedDB wrapper over db `atlas-dataset` v1. Five object stores — `meta`, `states`, `lgas`, `districts`, `areas` — all created with **no keyPath and no indexes**; composite out-of-line keys are passed at write time as arrays (`[state.code]`, `[state, lga]`, `[state, lga, district]`, `[state, lga, district, area]`). Reads use `IDBKeyRange.bound(prefix, [...prefix, '\uffff'])`. Has a full in-memory `Map` fallback (`MemoryDB`) used when `indexedDB` is unavailable (private mode); every read function try/catches to this fallback. `writeSnapshot` is one transaction across all stores with abort-on-error.
- **Dataset types (`dataset.ts`):** `AtlasState`, `AtlasLga`, `AtlasDistrict`, `AtlasArea`, `AtlasCounts`, `AtlasDatasetMeta`, `AtlasSnapshot`, `LocationCandidate`. All small.

### 2.3 NIPOST gateway client — `src/lib/api/postcodeClient.ts` (322 lines)

Class `PostcodeApiClient`, exported as singleton `postcodeApi`.

- **Single gateway method** `private gateway<T>(path, options)` (line 45–64): builds `${API_BASE}${path}`, adds `X-API-Key` header, `JSON.stringify`s the body, sends via `fetch`, unwraps `json.data ?? json`, and throws `Error("NIPOST gateway … failed: HTTP ${status}")` on non-2xx. Every other method is a thin wrapper on this.
- **Endpoint methods + cache TTLs** (in-memory `Map<string, {data, expires}>` with LRU-by-oldest eviction at 200 entries, per-call `pruneExpired`):

  | Method | Path | Cache key | TTL |
  |---|---|---|---|
  | `fetchStates()` | `/v1/reference/states` | `ref:states` | 1h |
  | `fetchLGAs(code)` | `/v1/reference/lgas?state=` | `ref:lgas:${CODE}` | 1h |
  | `fetchDistricts(state,lga)` | `/v1/reference/districts?state=&lga=` | `ref:districts:${S}:${LGA}` | 1h |
  | `fetchAreas(state,lga,district)` | `/v1/reference/areas?state=&lga=&district=` | `ref:areas:${S}:${LGA}:${D}` | 1h |
  | `lookupPostcode(code, level=1)` | `/v1/lookup?code=&level=` | `lookup:${CLEAN}:${LEVEL}` | 10m |
  | `reverseGeocode(lat,lng)` | `/v1/search/reverse?…&max_distance_m=250` | `rev:${lat.toFixed(5)}:${lng.toFixed(5)}` | 5m |
  | `fetchNearby(lat,lng,radius)` | `/v1/search/nearby?…&radius=` (clamped to 300) | `nearby:${lat.toFixed(4)}:${lng.toFixed(4)}:${radius}` | 3m |
  | `autocomplete(q)` | `/v1/search/autocomplete?q=` | — | uncached |
  | `disassemble(code)` / `assemble(segments)` | `/v1/assembly/disassemble|assemble` | — | uncached |
  | `getDiscoveryPoints()` | none | — | returns bundled array |
  | `getRandomDiscoveryPoint()` | none | — | random index |
  | `isConfigured()` | none | — | `Boolean(API_KEY)` |

- `lookupPostcode` (line 161–199) maps the gateway record into `PostcodeLocation`, splitting the code into 5 segments. `reverseGeocode` (205–235) does the same for a single record. `fetchNearby` (286–302) caps at 50 units.
- **Geo constants:** `NIGERIA_CENTER` is read from `src/lib/geo/nigeriaData.ts` (used as the map's resting viewport and as `App.tsx`'s initial `mapCenter`/`mapZoom`).

### 2.4 Static geo data — `src/lib/geo/nigeriaData.ts` + `discoveryPoints.ts`

- `nigeriaData.ts` (341 lines): hand-authored catalogue of all 37 states + FCT. Exports `NIGERIA_STATES: Record<string, StateGeoInfo>` (37 keys like `LA`, `FC`), `NIGERIA_CENTER: [9.082, 8.662]` (note: the file's comment says this is a centroid), `NIGERIA_DEFAULT_ZOOM = 6`. Each `StateGeoInfo` (`src/types/postcode.ts:40-48`): `{code, name, capital, zone, center:[lat,lng], zoom, lgaCount}`. Used by the map for framing and by `getState` lookup.
- `discoveryPoints.ts` (112 lines): the verified "Surprise me" landmark postcodes + the hunt targets. Returns `PostcodeLocation[]`. Used by `atlasStore.getDiscoveryPoints()` and by the hunt modal.

## 3. The Ask Atlas server side

### 3.1 Entry point — `api/ask.ts` (24 lines)

Vercel Node function (`runtime: 'nodejs'`, `maxDuration: 60`). Default export is `async function ask(request) { return handleAsk(request, process.env); }`. All env vars stay server-side; nothing is passed to the browser.

### 3.2 The handler — `src/server/ask/handler.ts` (444 lines)

`handleAsk(request, env)`: the production logic, shared with the Vite dev middleware (identical `handleAsk` call from `vite.config.ts:75`). It is the request boundary for Ask Atlas.

**Pipeline (one request):**
1. **POST-only.** Non-POST → 400 `bad_request`.
2. **Body-size guard.** `content-length` over 64,536 bytes → 400. Read body, parse JSON; non-JSON → 400.
3. **Validate fields:**
   - `text`: required, 1–500 chars after trim. Otherwise 400.
   - `language`: optional, must be one of `['en','yo','ha','ig']`. Otherwise 400.
   - `history`: optional array of `{role, content}`; sliced to last 10 entries (line 121/363); roles coerced to `assistant|user`, content trimmed; empty dropped. Anything else (ids, timestamps, context, location) stripped.
   - `context` → `sanitizeContext` (line 129–146): lenient. Accepts `selectedState`/`selectedLga` as objects (passed through as `{code,name}`), `selectedDistrict`/`selectedArea`/`selectedPostcode` as trimmed strings, **`referent`** via `sanitizeReferent` (see below), and `mapCenter` via `sanitizeMapCenter` (array of two finite numbers in range, else `[0,0]`). Unknown keys dropped. Returns `{selectedState?, selectedLga?, selectedDistrict?, selectedArea?, selectedPostcode?, referent?, mapCenter:[lat,lng], mapZoom:4}.`
   - `toolTurns` → `sanitizeToolTurns` (169–228): optional array; each entry `{assistantToolCalls:[{id,name,arguments}],[toolResults:[{tool_call_id,name,ok,data?,error?]}]}`; capped at 4 rounds, 8 messages per round, string-length limits on each field (id/name ≤64, arguments ≤4000, error message ≤400). **All-or-nothing:** a single malformed field returns 400 with a message. `tool_call_id` and `name` cross-checked; `ok:false` requires a well-formed `error` (`code` in the known set, non-empty message). This is the server's validation boundary; the client never re-sends malformed shapes.

4. **Provider resolution.** `resolveProviders(env)` (from `providers.ts`); if zero resolved → 503 `all_providers_unavailable`.
5. **Reply cache.** `replyCacheKey(language, text, context)` = JSON of `[lang, text.toLowerCase(), selectedState.code, selectedLga.code, selectedPostcode, referent.code]`. In-memory `Map` with 10-minute TTL, 200-entry LRU cap, pruned before lookup. Cache hit → returns immediately **with the original `engine` + `attempt`**. Misses cache the final answer only (tool-call rounds aren't cached because they depend on executed results).
6. **Prompt + messages.** `buildSystemPrompt(context, language)` (see §5 below) prepended, then the capped history, the user text, and the serialized client tool rounds.
7. **Chain run.** `runChain(env, messages, ATLAS_PROVIDER_TOOLS)` → `{text, toolCalls, provider, attempt}` or throws `ChainExhaustedError`.
8. **Response shaping.** `AskAtlasResponse = {text, grounding:'unverified', engine:{provider, model, attempt}, ...(toolCalls.length>0 ? {toolCalls} : {})}`. The server **does not** attach `lookup`/`results`/`decoded`/`nearby`/`mapAction`/`referent` — those are derived on the client. It only ever sets `grounding: 'unverified'`; the client upgrades to `'atlas'` when at least one tool succeeded (see §4). If it's a final text answer, it's cached.
9. **Error path.** Any `ChainExhaustedError` → 503 with `retryAfterSeconds`. Other throws → logged server-side, 503 generic copy. Provider internals are never leaked.

### 3.3 `sanitizeReferent` (feature 10, handler.ts:108–126)

Treats `context.referent` as untrusted client input: requires an object with a known `kind` (`'state'|'lga'|'district'|'area'|'postcode'`) and a non-empty string `code`; keeps optional string `name`/`state`; drops the entire field otherwise. So a malicious or malformed referent never reaches the prompt.

### 3.4 `serializeToolResult` / `narrowOversizedData` (handler.ts:245–294)

Bounds tool result JSON to ≤2000 chars. If over, it sends valid JSON that **labels itself as partial** (`{ok:true, data: {…}, truncated:true, note:"…PARTIAL. Treat it as incomplete…"}`) — never a mid-JSON-slice. Lists become `{items: [first 20], total: N, truncated:true}` so the model can state the real count; anything else becomes `{summary, keys}`.

## 4. The Ask Atlas client side

### 4.1 Request/response wire contract — `src/lib/ask/api-types.ts`

- `ASK_API_ENDPOINT = '/api/ask'`.
- `AskApiRequest = AskAtlasRequest`, `AskApiResponse = AskAtlasResponse`.
- `AskApiErrorResponse = { error: { code: 'bad_request' | 'all_providers_unavailable', message, retryAfterSeconds? } }`.
- The client posts `AskAtlasRequest` verbatim and reads back `AskAtlasResponse` verbatim.

### 4.2 Types — `src/lib/ask/types.ts` (249 lines)

The load-bearing contract. Key shapes:
- `AtlasContextSnapshot` (line 14–27): `{selectedState?, selectedLga?, selectedDistrict?, selectedArea?, selectedPostcode?, referent?, mapCenter:[lat,lng], mapZoom}`.
- `AtlasReferent` (34–39): `{kind:'state'|'lga'|'district'|'area'|'postcode', code, name?, state?}` — `state` carries the parent code for every kind below state.
- `ResponseGrounding = 'atlas' | 'unverified'`.
- `AskAtlasResponse` (55–103): `{text, grounding, engine?, location?, lookup?, results?, decoded?, nearby?, mapAction?, referent?, toolCalls?}`. `lookup`/`results`/`decoded`/`nearby`/`mapAction`/`referent` are **client-derived, absent on stub replies and on intermediate `toolCalls` responses**. `location` is slot-only (the panel may move the map on it, feature 8).
- `AskAtlasRequest` (137–150): `{text, context, history?, language?, toolTurns?}`.
- `AskToolCall` (158–162): `{id, name, arguments}` — `arguments` is the **raw JSON string**; parsed twice (client `executeToolCalls` and `runTool`).
- `AskToolResult` (165–171): `{tool_call_id, name, ok, data?, error?}`.
- `AskToolTurn` (174–177): `{assistantToolCalls, toolResults}` — one completed round.
- `AskAtlasMessage` (107–130): a conversation message carrying all the derived slots so the list can re-render without re-asking.
- `AtlasResultList` (192–204): `{level, scope?, scopePath?, items, total, units?, unitsTotal?}` — `scopePath` is `{state?, lga?, district?}`; `units`/`unitsTotal` are the bundled verified postcodes inside the scope (feature 5).

### 4.3 Transport hook — `src/lib/ask/useAskAtlas.ts` (98 lines)

Wraps the responder in a **TanStack Query `useMutation`**:
- `askReplyCacheKey(request)` (line 43–55): QueryKey over `[text, language, selectedState.code, selectedLga.code, selectedPostcode, **referent.code**]` — so the same words under a different referent miss the cache (feature 10 correctness). Conversation history is deliberately **not** part of the key. Cached answers stored via `setQueryData`.
- `retry: failureCount < 2 && error instanceof AskApiError && error.retryable` (90) with `sendRetryDelay` (92) = 1s/2s/4s exponential backoff. So transport-level retries are capped at 2, and only for `retryable` errors.
- `isReplying = mutation.isPending`.

### 4.4 The responder — `src/lib/ask/responder.ts` (830 lines)

Two implementations of `AskAtlasResponder.respond`:

**`createStubResponder()`** (line 82–97): for `VITE_ASK_MODE === 'stub'`. Fixed 400 ms latency, regex rules for "Lagos"/"postcode/decode"/"Ikeja etc", a `!fail`-to-throw escape hatch, and a static fallback. No tools. Used for offline/UI dev.

**`createApiResponder()`** (line 794–830): the real loop.
- Calls `postAsk({...request, toolTurns})` (line 802), which is a one-shot `POST /api/ask`.
- **Multi-round tool loop, capped at 3 client rounds** (`MAX_TOOL_ROUNDS = 3`, line 109; the server allows 4). Each round:
  - The server returns either a final answer (`toolCalls.length === 0`) or `toolCalls`.
  - If `toolCalls` empty → **final answer**. Grounds to `'atlas'` iff `grounded` (≥1 tool succeeded this loop) — done here client-side. Then attaches derived payload via `attachDerived`.
  - If rounds exhausted (`round === MAX_TOOL_ROUNDS`) while the model still wants tools → returns the truncated reply `TOOL_LOOP_EXHAUSTED_COPY` still with `attachDerived`.
  - Otherwise → `executeToolCalls(response.toolCalls)` (line 822) → appends a `toolTurns` entry and loops.
- `grounded` is `grounded || toolResults.some(r => r.ok)` — at least one tool call must have succeeded for the final answer to be `'atlas'`. A fully failed loop leaves it `'unverified'`.

**`attachDerived` (line 690–720)** — the heart of features 4–10. Runs purely client-side off the executed tool turns:
- `withLookup` → `deriveLookup` (196–216): the last successful `getPostcode` record, or the last single-landmark `searchLocation`. Yields `VerifiedLookup` (postcode, label, stateName, lgaName, coordinates, verified). Sets `lookup` and, if coordinates exist, a `location` slot for the map.
- `deriveResults` (422–434): the last list-producing result from `getStates`/`getLgas`/`getDistricts`/`getAreas`/`searchLocation`; each mapper (`resultFromStates`, `resultFromLgas`, etc.) builds the `AtlasResultList`. Then `withUnits` (388–395) appends the bundled verified postcodes whose scope matches `scopePath` (via `selectScopeUnits`, 364–381), capped at 8 for display.
- `deriveDecoded` (452–464): last successful `decodePostcode`, narrowed to `DecodedPostcode` (`{postcode, compact, display, valid, reason?, segments, stateName?, lgaName?, coordinates?, verified?}`). If valid + coordinates, also sets the `location` slot.
- `deriveNearby` (526–540): last successful `getNearby`; builds `NearbyResultList` reading the search origin/radius from the matching `assistantToolCalls` entry (`originFromCall`, 501–518) so the prose and the data agree.
- `deriveMapAction` (592–604): last successful `navigateMap`, narrowed by `asMapAction` (560–584) to one of the four validated `MapAction` variants. Only a tool-resolved action moves the map.
- `deriveReferent` (620–635): the conversation's "current place" — highest specificity wins (postcode 0, landmark 1, LGA 2, state 3), ties yield `undefined` (ambiguity → ask, not guess).

All derivables are **deterministic and pure** over `toolTurns`; no store reads inside them except `stateNameOf`/`lgaNameOf` (which read the local snapshot) and `selectScopeUnits` (reads bundled discovery points).

### 4.5 `runTool` boundary — `src/lib/tools/registry.ts`

The single validation boundary for client-side tool execution (line 119–157). Takes `(name, rawArgs)`:
- Unknown name → `{ok:false, error:{code:'unknown_tool'}}`.
- `schema.safeParse(rawArgs)` → on failure `{ok:false, error:{code:'invalid_args', issues[]}}`.
- `await execute(args)` → `{ok:true, data}`; throws `ToolFault` → `{ok:false, error:{code, message}}`; any other throw → `{ok:false, error:{code:'internal_error'}}`. **Never throws itself.**

The registry maps the 10 `TOOL_NAMES` (`searchLocation, getState, getStates, getLgas, getDistricts, getAreas, getPostcode, decodePostcode, getNearby, navigateMap`) to their zod `Schemas` + `executors`.

### 4.6 Tool schemas — `src/lib/tools/schemas.ts`

Zod schemas that are the **single source of truth** for both runtime validation and the provider `tools` JSON Schema (via `z.toJSONSchema`, `provider.ts:59`). Each takes name-or-code strings, except `getNearby` (`lat/lng` finite + range checks, optional `radius`) and `navigateMap` (a `z.discriminatedUnion('target', …)` requiring exactly one of `{state, lga, postcode, reset}`). `TOOL_DESCRIPTIONS` (line 81–93) is the per-tool one-liner the model sees.

### 4.7 Provider tools — `src/lib/tools/provider.ts`

`ATLAS_PROVIDER_TOOLS: ProviderTool[]` (line 69) — the OpenAI-compatible `tools` array serialized once at module load from the schemas + descriptions. Imported by `handler.ts:15` and passed to every `runChain` call.

### 4.8 Tool executors — `src/lib/tools/executors.ts` (299 lines)

The 10 client-side implementations, all read-only, all reading the local cache first:
- `searchLocation` → `atlasStore.searchLocations`.
- `getStates` → `atlasStore.getStates`.
- `getState` → resolves state, enriches with `NIGERIA_STATES` geo (capital, zone, center, zoom, lgaCount); returns `StateSummary`.
- `getLgas` → resolves state, then `atlasStore.getLgas`.
- `getDistricts`/`getAreas` → resolve state + lga (+ district), then `atlasStore.getDistricts`/`getAreas`, capped to `HierarchyPage<T>` via `toHierarchyPage` (MAX_HIERARCHY_ROWS=50, with real `total`/`truncated`).
- `getPostcode` → `atlasStore.getPostcode` (landmarks first, then gateway); `null` = unmapped.
- `decodePostcode` → normalizes via `toDashedCode` (handles both dashed `LA-11-A12-AK-08` and 11-char compact), regex-validates the 5-segment shape, then resolves names from the snapshot + gateway `getPostcode`. Returns `DecodedPostcode` with `valid`/`verified` semantics: `verified: lookup ? lookup.verified !== false : false` (a decoded code is confirmed only when the full postcode mapped to a record).
- `getNearby` → `postcodeApi.fetchNearby` clamped to 300 m, capped at 50 units, mapped to `NearbyUnit[]` (flips `[lng,lat]`→`[lat,lng]`).
- `navigateMap` → **returns a `MapAction`, never moves the map itself.** reset/state/lga/postcode, each validated: resolves the place from the store, looks up `NIGERIA_STATES` geo for center+zoom, throws `ToolFault('not_found')` on an unmapped place. A postcode action requires lat/lng. This is the contract the panel relies on — feature 8.

### 4.9 The provider chain — `src/server/ask/providers.ts` + `chain.ts`

**`providers.ts` (306 lines):** OpenAI-compatible provider registry.
- `AskProviderId = 'gemini' | 'openrouter' | 'nvidia' | 'natlas'`.
- `REGISTRY` for the three always-present providers: base URLs hardcoded (`generativelanguage.googleapis.com/v1beta/openai`, `openrouter.ai/api/v1`, `integrate.api.nvidia.com/v1`), default models (`gemini-3.1-flash-lite`, `nvidia/nemotron-3-ultra-550b-a55b:free`, `nvidia/nemotron-3-super-120b-a12b`), key env names (`GEMINI_API_KEY`/`GEMNINI_API_KEY` typo alias, `OPENROUTER_API_KEY`, `NVIDIA_API_KEY`).
- `resolveProviders(env)`: the optional `natlas` slot is **prepended** when `NATLAS_BASE_URL` is set (key + model optional, defaults `NCAIR1/N-ATLaS`). Each of the three always-present providers is added only if its key resolves via `firstKey`. Model overrides: `ASK_AI_MODEL_<PROVIDER>`.
- `callProvider(provider, messages, tools?, timeoutMs=15000)`: one POST to `${baseUrl}/chat/completions`, `Authorization: Bearer <key>` when a key exists, `temperature: 0.4`, optional `tools`. Parses `choices[0].message` into `{text, toolCalls}`. HTTP errors → `ProviderError` with a `kind` (`rate-limited` from 429 + Retry-After, `quota` from 401/403, `bad-request` from 400, `server` from 5xx/network). A `bad-request` with tools is retried once without tools so the chat degrades to text.
- `ProviderError` carries `kind` + optional `retryAfterSeconds`.

**`chain.ts` (162 lines):** failover scheduler.
- `resolveOrder(env)`: `ASK_AI_ORDER` overrides; default `gemini, openrouter, nvidia`; `natlas` prepended when `NATLAS_BASE_URL` set.
- `runChain(env, messages, tools)`: walks the order, **skips providers with no key** and **skips those in cooldown** (see below). Each attempt counts toward `attempt` (1-based) so the response shows where the chain landed. Returns `{text, toolCalls, provider, attempt}` or throws `ChainExhaustedError` (with the earliest cooldown end as `retryAfterSeconds`).
- **In-memory cooldown ledger** (per warm instance, best-effort, lost on serverless reset): 429 → 10 min (or Retry-After floored at 30 s), 401/403 → 15 min, 5xx/network → 30 s. Never retries the same failing provider within the cooldown window.

### 4.10 The system prompt — `src/server/ask/prompt.ts` (183 lines)

`buildSystemPrompt(context, language)`: one string per request, assembled from `[...].join('\n')`. Built blocks:
1. Role: "You are Ask Atlas, the Nigerian postcode assistant built on N-ATLAS."
2. Tone: "Answer briefly, factually, and in plain language."
3. Reply language (English / Yoruba / Hausa / Igbo).
4. Map scope: `describeSelection(context)` → `"map center <lat,lng>, state <name>, LGA <name>, district …, area …, postcode …"` or "Nigeria (no state selected)".
5. **Hard scope:** answer ONLY questions about Nigerian postcodes/states/LGAs/districts/areas/the Atlas platform; refuse everything else and offer to look up a Nigerian place instead.
6. **Tool-use rules** (features 2–9): call the right tool for real data; disambiguate via `searchLocation`; never invent; state postcode/district/area/unit only from tool results and mark general-knowledge claims as unverified; list hierarchy from results and say how many you received when `truncated`; decode per the 5-segment rule and respect `verified:false`; nearby queries need a real coordinate resolved from map center / landmark / postcode / typed lat-lng, never a place name in the coordinate slots; navigate via `navigateMap` with a real target, resolved through `searchLocation` when needed.
7. **`referentBlock(context)` (feature 10, line 133–151):** emitted **only when there's something to resolve against** — a reply-derived referent (`referentPhrase`, naming the kind/code/name and parent state) or, failing that, a map selection (`selectionPhrase`). Tells the model to resolve "it"/"that place"/"there"/"its" against it, prefer a newly named place, ask rather than guess when nothing resolves, and "never treat an earlier postcode, district, or area as a place of its own." Absent on a bare first question.

The model never sees raw user text in the system prompt; every prompt is derived from the validated request.

Built on `react-leaflet` + raw `leaflet`. `<MapContainer center={NIGERIA_CENTER} zoom={6} minZoom=5 maxZoom=19 zoomControl={false}>`. Three child controls expose map instance via `useMap()`:

### 5.4 Ask Atlas panel + sub-components

`AskAtlasPanel` (206 lines) owns the conversation: `messages: AskAtlasMessage[]`, `input`, `language: AskLanguage`, `listHeight`. It wraps `useAskAtlas(responder)` for the mutation/cache, and builds each request as `{ text, context: {...getContext(), referent: latestReferent(messages) }, history: messages, language }` — the **entire** current message list is the history (the server caps it to 10). `latestReferent` (47–53, exported for probing) scans messages newest-first for the last assistant message with a `referent`. On send, the user turn is appended with its `context` snapshot, so the server prompt can echo it. On reply, **every** derived slot (`lookup`, `results`, `decoded`, `nearby`, `mapAction`, `referent`, `location`) is copied onto the message and the message is appended; `mapAction` immediately calls `onMapAction`.

Sub-components (children of the panel, all receive a single `message` or slice):
- `AskAtlasHeader` (86 lines): language chip group (en/yo/ha/ig), clear button, close (×). `AskLanguage` typed in `types.ts`.
- `AskAtlasMessageBubble` (127): switch on `message.role`. Assistant bubbles render **all** derived payloads: `lookup` as a chip, `decoded` as the decode card, `results` as the list, `nearby` as the nearby list, `mapAction.location` via `onViewLocation`, and `mapAction` via `onMapAction`. The model's `text` is rendered as prose. (Tool-call rounds never reach the panel — the client consumes them silently.)
- `AskAtlasThinkingBubble` (56): the "… is thinking" ellipsis.
- `AskAtlasComposer` (57): textarea with char counter + send; 300-char wrap assumed.
- `AskAtlasDecodedCard`, `AskAtlasResultsList`, `AskAtlasNearbyList`: pure renderers of their respective typed slots.
- `AskAtlasResizeHandle` (69): drags the conversation list height.

## 8. End-to-end request flow (example: "what are the LGAs in Lagos?")

1. **Shell.** User opens the Ask Atlas panel (App sets `isAskAtlasOpen=true`, renders `<AskAtlasPanel responder={askResponderRef.current} getContext={getAskAtlasContext} onMapAction={handleMapAction} onViewLocation={handleViewLocation}/>`).
2. **Compose.** User types the question, hits send. `handleSend`:
   - builds `context = {...getContext(), referent: latestReferent(messages)}`;
   - appends the user message (with its `context` snapshot) to `messages`;
   - calls `send({text, context, history: messages, language})` from `useAskAtlas`.
3. **Cache check.** `useAskAtlas` mutationFn computes `askReplyCacheKey(request)` and returns a cached answer if present (skipping the network + provider entirely). On a miss, calls `responder.respond(request)`.
4. **Loop round 0.** `createApiResponder` calls `postAsk({...request, toolTurns:[]})` = `POST /api/ask`.
   - Handler: validates body (64 kB cap, text 1–500, language in set, history capped to 10 stripped to `{role,content}`, context sanitized incl. `referent`, toolTurns `[]` so skipped).
   - Cache miss → `buildSystemPrompt(context, 'en')` + history + user text + no tool messages.
   - `runChain(env, messages, ATLAS_PROVIDER_TOOLS)`: walks gemini→openrouter→nvidia (skipping the keyless/cooldown ones), 15 s timeout each, tools attached. Returns the first provider that answers with text **or** tool_calls.
5. **Model.** The prompt's scope guard + exploration rule nudges the model to call a tool. It emits `getLgas` with `{state:"LA"}` (the model read the Lagos context from the prompt's map-scope line, or matched the name).
6. **Client executes (round 0).** `executeToolCalls` → `runTool('getLgas', {state:"LA"})`:
   - zod-validates args; `runTool` dispatches to `executors.getLgas`.
   - `getLgas` → `resolveState("LA")` (checks `atlasStore.getStates()` which hits IndexedDB or gateway) → `atlasStore.getLgas("LA")` (IndexedDB or gateway fallback) → returns 20 `AtlasLga[]`.
   - Result: `{ok:true, data: [{state:"LA",code:"01",name:"Agege"}, …]}`.
   - `grounded = true` (≥1 ok).
7. **Loop round 1.** A new `toolTurns` entry `{assistantToolCalls:[{id,name:'getLgas',arguments:'{…}'}], toolResults:[{tool_call_id,name:'getLgas',ok:true,data:[…]}]}` is appended; `postAsk` again. Handler re-validates, cache-misses (tool rounds aren't cached), rebuilds the prompt with the tool result injected as a `tool` message, runs the chain again.
8. **Model round 1.** Now with real data, answers in English: "Lagos State has 20 LGAs: Agege, Ajeromi-Ifelodun, …" with no further tool calls.
9. **Client finalizes (round 1 = MAX_TOOL_ROUNDS).** `response.toolCalls.length === 0` → final answer path. `attachDerived(response, toolTurns)`:
   - `deriveLookup` — no `getPostcode`/single-landmark, so no `lookup`.
   - `deriveResults` — last list-producing result is the `getLgas` round → `resultFromLgas` maps to `AtlasResultList{level:'lga', scope:'Lagos', scopePath:{state:'LA'}, items:[…], total:20}`, then `withUnits` appends any bundled landmarks in scope (none here beyond what's already listed).
   - `deriveDecoded`/`deriveNearby`/`deriveMapAction`/`deriveReferent` — none this turn. But `deriveReferent` would pick the LGA (rank 2) as the next turn's referent.
10. **Grounding flag.** Because `grounded`, the client overwrites `response.grounding` to `'atlas'` before returning (the server left it `'unverified'`).
11. **Cache + render.** `useAskAtlas` stores the reply under `askReplyCacheKey` (includes `referent.code`) and returns it. `handleSend` builds an `AskAtlasMessage` with **all** the derived slots (`results`, `referent`, etc.) and appends it; `AskAtlasMessageBubble` renders the prose + the `AskAtlasResultsList`. The `referent` (LGA Agege/LA) is stored on the message and becomes `latestReferent(messages)` for the next turn.
12. **Follow-up.** If the user now says "what are its districts?", the new request carries `referent={kind:'lga',code:'01',state:'LA'}` (from step 2), the prompt's `referentBlock` tells the model to resolve "its" against that LGA, and `getDistricts` is called with the right codes.

A map-navigation request ("show me Benue") differs only at step 5/6: the model calls `navigateMap{target:'state',state:'Benue'}` → `executors.navigateMap` resolves Benue, returns a validated `MapAction` → `deriveMapAction` → `handleMapAction` → `handleSelectState` → flyTo + breadcrumbs + toast. The model never touches map state directly.

## 9. Notable properties & asymmetries (for reviewers)

- **`readPendingUpdate` (version.ts:118–124) is exported but unused** by App — a persisted pending update is not rehydrated on mount (cleared instead).
- **`handleSelectLGA` (App 239–253) does not update the URL `code`** — unlike state/location select which call `updateUrlLocation`. An LGA selection is not deep-linkable.
- **District/area IndexedDB stores are permanently empty** by design (snapshot ships `[]` for them); `getDistricts`/`getAreas` always gateway-fallback today.
- **`dev` port is 3001**, but `AGENTS.md` (the onboarding section) claims 3000; `start`/`preview` use Vite's default 4173.
- **`NIPOST_PLATFORM_BASE_URL`** exists in the local `.env` but is referenced nowhere in `src/` or `scripts/`.
- **`VITE_ASK_MODE`** is a functional client flag but undocumented in `.env.example`.
- No `headers` in `vercel.json` — `/atlas-data.json` relies on default Vercel caching, mitigated client-side by the cache-busting fetch.
- No TTL sweeper for the `postcodeClient` in-memory cache beyond expiry-on-read; long sessions accumulate entries per distinct LGA/LGA/district/area/nearby coordinate.
- The provider base URLs and the OpenAI-compat shape are hardcoded assumptions; N-ATLAS is "assumed OpenAI-compatible (Awarri docs unverified)".
- Version hydration uses **exact string match** (`meta.version === APP_VERSION`), not `compareVersions` — a content-identical bump still re-downloads.
